Requirements
Comments and Requirements
noreferences
@@tooltip Defined requirements can be implemented multiple times throughout the code through an implementsReq statement.

@@description
Requirements allow for the same comment to appear in different sections of the code without typing out the comment multiple times.

<p>They consist of two components: the requirement definition, which contains the comment statement to be added, and the requirement implementation, which specifies where the requirement statement should be added.<p>

<p>Multiple requirements can be called through an implementsReq statement.<p>

<br />

<p>A requirement can be tagged with multiple entities like classes, attributes, associations, state machines, traits, methods, interface etc.<p>

<br />

<h3>Requirement-definition syntax</h3>

<p>A requirement is introduced with the <code>req</code> keyword, followed by an identifier and an optional requirement-language tag. The body is enclosed in curly braces:</p>

<pre>
req &lt;ReqIdentifier&gt; [&lt;reqLanguage&gt;] { ... }
</pre>

<p>The supported requirement languages are:</p>

<ul>
  <li><b>plain</b> (default, tag may be omitted) &mdash; free text.</li>
  <li><b>userStory</b> &mdash; free text optionally structured with <code>who</code>, <code>when</code>, <code>what</code>, and <code>why</code> sub-blocks.</li>
  <li><b>useCase</b> (also written <code>usecase</code>) &mdash; free text, or the steps of an interaction between an actor and
      the system. See the section below.</li>
  <li><b>ears</b> &mdash; free text, or the clauses of the Easy Approach to Requirements Syntax, which read as a single sentence
      such as <i>While ..., when ..., the ... shall ...</i>. See the section below.</li>
  <li><b>quality</b> &mdash; introduces named quality classes (e.g. <i>High</i>, <i>Medium</i>, <i>Low</i>) for a non-functional property. See <a href="RequirementQualityClasses.html">Requirement Quality Classes</a>.</li>
</ul>

<h3>useCase requirements</h3>

<p>A <code>useCase</code> requirement describes an interaction between an actor and the system. Its body may be free text, or may be
structured with any combination of the sub-blocks below, written one per line and in any order:</p>

<ul>
  <li><code>who</code>, <code>when</code>, <code>what</code> and <code>why</code> &mdash; the same sub-blocks used by
      <code>userStory</code> requirements.</li>
  <li><code>userStep &lt;id&gt; { ... }</code> and <code>systemResponse &lt;id&gt; { ... }</code> &mdash; the steps of the scenario.
      The identifier may be a number or alphanumeric, and the steps are kept in the order they are written.</li>
  <li><code>isA &lt;ReqIdentifier&gt; [, &lt;ReqIdentifier&gt;]* ;</code> &mdash; the use case is a special case of the named use
      cases, as with UML generalization.</li>
  <li><code>include &lt;ReqIdentifier&gt; [, &lt;ReqIdentifier&gt;]* ;</code> &mdash; the use case incorporates the steps of the
      named use cases, as with the UML include relationship.</li>
</ul>

<p>A step may carry a condition in square brackets, written like a state machine guard. The step applies only when the condition
holds, so several steps can share one identifier to describe alternative outcomes of the same point in the scenario:</p>

<pre>
req UC5 useCase {
  isA UC3;
  include UC4;
  userStep 1 { select a payment method }
  systemResponse 1 [card accepted] { confirm the order }
  systemResponse 1 [card declined] { ask for another card }
}
</pre>

<p>See <a href="RequirementsExamples.html">Requirements Examples</a> for complete useCase models in plain, structured and related forms.</p>

<h3>ears requirements</h3>

<p>An <code>ears</code> requirement is written with the Easy Approach to Requirements Syntax (EARS), in which a few keywords
give natural language requirements a consistent structure. Its body may be free text, or may be structured with the clauses
below, written in any order. A clause starts a line or follows another clause, and may span several lines.</p>

<ul>
  <li><code>where { ... }</code> &mdash; the optional feature that must be included for the requirement to apply.</li>
  <li><code>while { ... }</code> &mdash; the precondition, typically a state, during which the requirement applies.</li>
  <li><code>when { ... }</code> &mdash; the event that triggers the response.</li>
  <li><code>if { ... }</code> &mdash; an unwanted event, such as a failure or a user error, that triggers the response.</li>
  <li><code>system { ... }</code> &mdash; the name of the system that responds. If it is omitted, <i>the system</i> is used.</li>
  <li><code>shall { ... }</code> &mdash; what the system shall do in response. A structured ears requirement needs this clause;
      warning 410 is issued when no occurrence of the requirement gives it.</li>
</ul>

<p>The clauses are combined, in the order EARS prescribes, into a single sentence that appears in generated requirements
documents and in the comments of generated code. The EARS patterns are formed as follows:</p>

<ul>
  <li><b>Ubiquitous</b> (<code>shall</code>) &mdash; <i>The &lt;system&gt; shall &lt;response&gt;</i></li>
  <li><b>State-driven</b> (<code>while</code>) &mdash; <i>While &lt;precondition&gt;, the &lt;system&gt; shall &lt;response&gt;</i></li>
  <li><b>Event-driven</b> (<code>when</code>) &mdash; <i>When &lt;trigger&gt;, the &lt;system&gt; shall &lt;response&gt;</i></li>
  <li><b>Optional feature</b> (<code>where</code>) &mdash; <i>Where &lt;feature is included&gt;, the &lt;system&gt; shall &lt;response&gt;</i></li>
  <li><b>Unwanted behaviour</b> (<code>if</code>) &mdash; <i>If &lt;trigger&gt;, then the &lt;system&gt; shall &lt;response&gt;</i></li>
  <li><b>Complex</b> (several of the above) &mdash; <i>Where ..., while ..., when ..., if ..., then the &lt;system&gt; shall &lt;response&gt;</i></li>
</ul>

<p>For example, the following reads <i>While the aircraft is on ground, when reverse thrust is commanded, the engine control
system shall enable reverse thrust</i>:</p>

<pre>
req EARS6 ears {
  while { the aircraft is on ground }
  when { reverse thrust is commanded }
  system { engine control system }
  shall { enable reverse thrust }
}
</pre>

<p>EARS allows several preconditions and several responses, so a clause given more than once, in one or several occurrences
of the requirement, is joined to the earlier one with <i>and</i>. Any text in the body outside the clauses is kept, and is
shown after the sentence.</p>

<p>The clauses correspond closely to Umple constructs, which helps when turning ears requirements into a model: a
<code>while</code> precondition usually becomes a state of a state machine, a <code>when</code> or <code>if</code> trigger
an event, a <code>shall</code> response a transition or action, and a <code>where</code> feature a
<a href="BasicMixsets.html">mixset</a>. See <a href="RequirementsExamples.html">Requirements Examples</a> for a model built
this way.</p>

<h3>implementsReq statement</h3>

<p>An <code>implementsReq</code> statement attaches one or more requirements to the surrounding entity. It can appear at the top level (binding to a following mixset or class), inside a class, trait, state machine, attribute, association, or method:</p>

<pre>
implementsReq &lt;ReqIdentifier&gt; [(&lt;QualityClassName&gt;)] [, &lt;ReqIdentifier&gt; [(&lt;QualityClassName&gt;)]]* ;
</pre>

<p>The optional parenthesised argument selects a specific quality class of the referenced requirement, which is required when using <code>implementsReq</code> to differentiate alternative designs on a non-functional property:</p>

<pre>
implementsReq Speed(High), Security(Perfect);
mixset DesignA { ... }
</pre>
